# `down --shared -n` tears down one namespace's shared services

ADR-0010 made shared services namespaced and lazily added, but kept teardown all-or-nothing: an added shared service stays in the shared instance until `devtrees down --shared`, which stops every shared service under every worktree. So the only way to recover one dead or drifted namespaced shared service (`SHARED_SERVICE_DEAD`, `SHARED_DRIFT`), or to apply a changed definition of it, was to stop all of them (#239, found while reviewing #237; the core consumer's DEV-1085).

## Decision

**`devtrees down --shared -n <namespace> [-n <namespace>…]`** stops and removes only the shared services of the named namespaces. Everything below happens under the shared lifecycle lock, the one `up` holds while it lazily starts the shared instance, adds a namespaced shared service (ADR-0010) or restarts a dead one (#240, ADR-0008). So a teardown never interleaves with any of them.

1. **Targets.** A target is a process of the shared derived config (what the shared instance runs, not this worktree's `devtrees.yaml`) that declares a `namespace:` with one of the named namespaces among them, the same "any of its namespaces" rule `up` selects by. An always-on shared service declares no namespace, so it is never a target, not even of `-n default`: only a full `down --shared` stops it.
2. **Nothing to do is a no-op.** No shared instance running, or no target among the named namespaces: exit 0, `stopped: false`, and each named namespace with no target is listed in `inactive_namespaces`. That holds for a misspelt namespace too. An error was considered for that case. But `down` is idempotent everywhere else, and a retried `down --shared -n a` after a success must succeed. A shared namespace is also only visible once some `up` has added it, so devtrees cannot tell "not started yet" from "wrong name". One rule covers every case: no-op, and say which namespaces had nothing.
3. **Dependants refuse it.** The teardown fails `SHARED_IN_USE` and stops nothing while something still depends on a target. `details.dependants` lists each one as `{instance, service, depends_on, source}`:
   - **a live worktree instance's booted isolated service** that `depends_on` a target (`instance` is the worktree id). `--force` overrides this; the dependant keeps running without its dependency, exactly as it does after a full `down --shared`.
   - **a shared service the teardown would keep** that `depends_on` a target (`instance: shared`). `--force` does not override this. Removing the dependency from that service's running definition would change its process config, and process-compose restarts a process whose config changed: the interference ADR-0008 forbids. Leaving it as is would hand process-compose a config whose process depends on one that is gone. So the remedy names that service's namespaces too (`-n a -n b`), or `down --shared` for an always-on one. `details.forceable` says which case it is.
4. **The last running shared services** are a full `down --shared`, exactly as today: same bounded stop, same config removal, `instance_stopped: true`. process-compose exits once nothing runs, so removing them one by one would end the instance anyway, only less cleanly. "Last" means no kept service is running now (`keepsInstanceAlive`): a finished one-shot or a `Pending` service does not count.
5. **Otherwise, stop then remove.**
   - The running targets are stopped with `restart`'s bounded stop (ADR-0009): `process stop` runs each one's `shutdown` hook, the services' process groups get the same budget and force-kill as `down` (#190, #155), and the daemon hooks process-compose skips are run from the anchor. A refused or unfinished stop fails `SHARED_REMOVAL_FAILED` (`stop_refused`, `stop_incomplete`) with nothing removed, so a retry finds the same targets.
   - Then the targets' processes are dropped from the shared derived config and process-compose re-reads it (`POST /project/configuration`), the reload activation uses (ADR-0010). The kept processes are byte-for-byte unchanged, so process-compose leaves them running with the same pids. The reload only removes processes that are already stopped. Stopping first, rather than letting the reload stop them, keeps the bounded stop's escalation: a reload has none (ADR-0009).
   - A refused reload (`not_supported`, `error`) restores the previous config. The services stay listed, stopped, and a retry removes them. A timed-out one keeps the new config, because process-compose may still apply it. The retry re-sends the reload while the instance still lists a process the config no longer holds, and reports what it removed in `removed` with `stopped: false` (nothing was running to stop).
   - If no retry comes and an `up -n <namespace>` adds the services back first, the add re-sends their unchanged definition, which process-compose leaves as it is: stopped. So an add that finds an added service already listed in the project starts it, as it would a dead shared service (#240), reports it in `shared_restarted`, and waits for it to be healthy.
6. **The drift record goes with them.** The targets' entries in `shared-state.json` `services` (their revision, ADR-0010) and `extended` (#185) are dropped. The next `up -n <namespace>` finds no record, so it adds the services with its current definition, and no `SHARED_DRIFT` can come from the definition they ran. That is the point of the command for a drifted service.
7. **Their ports leave the running state; the port map keeps their numbers.** `shared-state.json` `ports` records what the running instance binds, and the stable shared port map (#238, `shared-ports.json`) reads it that way (a running instance's numbers, checked against the map). The targets bind nothing once removed, so their named ports are dropped from `ports`, except one a kept service also owns. Their numbers stay reserved in the port map, which only grows: `env` keeps injecting them, and adding the services back binds the same numbers again. Keeping them in `ports` was rejected: the state would claim the running instance binds a port it does not. Between the teardown and the re-add, `env --json` reports such a port with origin `recorded`, and `active` again once an `up` adds the service back (smoke 124).
   - **`prune --shared-ports` (ADR-0011) and a removed service.** Prune drops a recorded name only when nothing holds it: neither the running instance's `ports` nor the env of any derived config on disk. After the teardown, `ports` no longer holds it, but every derived config still carries it in env as long as some stack declares the service. Every worktree config, and every shared process that keeps running, injects every shared service's named port, selected or not. So in practice the number stays reserved while any worktree still declares the service, and prune can drop it once none does and their configs are gone or re-derived. This is intended: a namespaced teardown is a restart of one namespace, not the end of the service, and its port must survive it. The teardown never writes `shared-ports.json` itself.
   - **No new conflict.** The kept shared processes' env still carries the removed service's number, and that number is the map's, so a later `up` sees no `bound_mismatch` or `port_taken` from it. The re-add binds the map's number, which those env entries already agree with.

**How dependants are found.** devtrees keeps no reference count (ADR-0001), and the worktree derived config drops cross-tier edges (ADR-0003). So the deriver now records them: the worktree config's `x-devtrees.shared_depends_on` maps each isolated service to the shared services it depends on. It is written in every worktree config, `{}` when no edge was dropped, and it is the edge set the instance actually booted with. Writing it changes no running instance: convergence compares `stackHash`, and process-compose ignores `x-` keys. The teardown discovers every worktree instance from the run dir, as `ls` does, the caller's own included, and skips one whose socket is definitively stale. For each, it reads the edges from its derived config. Only an instance started before #239 has no such key; its edges are read from that worktree's `devtrees.yaml`, found through the config's `working_dir`. An instance whose edges cannot be read either way counts as a dependant (`source: unknown`, `service: null`), because guessing "no dependants" could pull a database from under a running worktree. `--force` overrides that too. Only a booted service counts: one in the instance's `process list`, or one a pending hot-reload (#191) is applying, which process-compose stops listing while its old run is still alive (the same rule `ls` reads booted namespaces by). A service in a namespace the worktree did not boot does not block. When the list cannot be read, every recorded edge counts.

**An `up` in flight is a dependant too.** A fresh `up` takes its worktree's lifecycle lock, does its shared step under the shared lock, then, still holding the lifecycle lock but no longer the shared one, waits for the shared services' health and spawns its worktree instance. Until its socket is bound, discovery cannot see it. So the teardown also lists the anchor's lifecycle lock files (`<worktree id>.lock`; never `registry.lock`, `shared.lock` or `hashes.lock`), after the discovery, and a worktree whose lock is held by a live process (the check `stealIfStale` makes) is a dependant with `source: lifecycle_in_progress`, `service: null`, also when its instance was already listed by its edges (the command may be changing them). It takes no lock and steals nothing. The scan is `heldWorktreeLocks` in `registry.ts`, the same one `prune --shared-ports` (ADR-0011) refuses on through `assertNoWorktreeLifecycleLocks`: both run under the shared lock, and both skip the shared, registry and hashes locks. An `up` is therefore seen either by its socket or by its lock.

**An in-flight command is waited for, never forced.** The lock check also catches commands that do not use the targets: an `up` of another namespace, a `down` in its bounded stop, or an `up` queued on the shared lock behind this very teardown. Refusing at once, with `--force` as the remedy, would steer an agent to pull the services from under exactly the `up` the check protects. So:

- When the only blockers are in-flight commands (and worktree dependants, which `--force` may override), the teardown **releases the shared lock**, polls the lock files until those commands finish, and then starts over: it takes the shared lock again and redoes every read. It waits up to 15s in all. It must not wait while holding the shared lock: an `up` queued on it holds its own worktree lock until it is through, so it could never finish, and the teardown would always run out the clock. Starting over also sees what the finished `up` started. If that `up` now depends on a target, it is an ordinary worktree dependant.
- A shared dependant fails at once: waiting cannot clear it.
- If a command is still in flight after the wait, the teardown fails `SHARED_IN_USE` with `forceable: false`. Its `details.remedy` is the plain retry, without `--force`, even when the caller passed `--force`. The message names the lock files, in case one is stale (a pid that is not a process's, left by hand).
- `--force` never overrides an in-flight command, only a worktree that uses the services. Such a command clears on its own, and forcing under an `up` that is waiting for shared health would fail it as a misleading `SHARED_SERVICE_DEAD` (`died_while_waiting`).
- `--force` is the remedy only when every remaining blocker is a real worktree dependant (`derived_config`, `devtrees_yaml`, `unknown`).
- The dry run does not wait; it reports an in-flight command as blocking.

**Amended (#243/#244 review follow-up): in-flight blocking is scoped to the targets.** The lock check above blocked on every in-flight command, including an `up` of other namespaces and a worktree `down`, which never use the targets. Now:

- **The shared-step marker.** Under the shared lock, the shared step of `up` writes `<anchor>/devtrees/<worktree id>.shared-step.json`: the shared services it uses and the shared ports it injects, with the holder's pid and the inode of its lifecycle lock file. An `up` of a stack with no shared tier writes one naming nothing (without the shared lock: nothing it claims can change under a teardown), and so does a worktree `down`, whose marker names no ports.
- **Which services it names.** The ones the `up` selected, **plus** the shared targets of the cross-tier `depends_on` edges of the isolated services it boots (`sharedStepServices`). Selection never pulls in a shared service an isolated one depends on (ADR-0010), yet that isolated service starts against it, so without these the teardown could remove it during the `up`'s health wait or spawn: a regression against the plain lock check, found in review. A fresh `up` counts the isolated services it selects; an `up` on a running instance counts every isolated service of the stack, because a hot-reload may start any of them (process-compose stops listing a service while it updates it, and the pending-reload record is written only on a timeout).
- **Validity.** A marker counts only while its worktree's lock file is the one it names and is held by its pid. It is removed before the lock is released (marker first, so a reader that still sees the lock sees at worst no marker), and a new holder of the lock removes any it finds. A crash leaves both; the dead pid makes the lock not held and the marker stale. A stolen lock has another pid (and file), so a stale marker never stands in for a live `up` that has not reached its shared step.
- **Who blocks.** The teardown blocks on an in-flight worktree whose valid marker names a target (`depends_on` lists those targets), or that has no valid marker: an `up` not yet past its shared step, or a `restart`. That is the conservative case. Its wait now ends as soon as no waited-for worktree blocks any more, so an `up` that gets past its shared step without a target releases the teardown without its lock being released.
- **Stale markers** are removed by the teardown and by `prune --shared-ports`, under the shared lock: markers are written only under that lock, so none can appear while they decide. The dry run removes nothing.
- **Lock order is unchanged.** Nothing waits on a worktree lock while holding the shared lock; the marker is read, never locked.
- **`details` change:** a `lifecycle_in_progress` dependant's `depends_on`, always `[]` before, now lists the targets an in-flight `up`'s marker names.

**Amended (same follow-up): the recovery remedy reads the running config.** `namespacedRecoveryRemedy` built the namespace closure from this worktree's `devtrees.yaml`. The teardown picks its targets, and refuses on shared dependants, from the running shared derived config, and in the drift case the two can differ (a service moved to another namespace, an edge added or dropped). The remedy now reads the namespaces and the closure from the running shared derived config whenever it runs every named service, and falls back to the stack otherwise. The `up` half stays this worktree's. Release notes: `SHARED_DRIFT` / `SHARED_SERVICE_DEAD` `details.remedy` can name different namespaces than before when the running definition differs.

**Dry run.** `down --shared -n … --dry-run` (with `--json`, `down_dry_run`) makes the same reads without the shared lock, leaves a stale socket file in place, and stops, reloads and writes nothing. It reports `services`, `inactive_namespaces`, `would_stop_instance`, every dependant, and `blocked` (whether the real run, with the same `--force`, would fail `SHARED_IN_USE`). It exits 0 even when blocked: the preview is the answer.

**Flags.** `-n` is accepted only with `--shared`. A plain `down -n` was an unknown-option usage error, and it stays an error, now `INVALID_ARGS`, so `down` keeps its meaning: a worktree's `down` stops its whole instance (the persistent worktree `down -n` stays deferred, ADR-0009, #171). `--force` and `--dry-run` without `--shared -n` are `INVALID_ARGS` too. `down` and `down --shared` without `-n` are unchanged, byte for byte.

## Consequences

- Amends ADR-0010's "An added service **stays** until `devtrees down --shared`" and its last consequence ("A per-namespace shared teardown is not provided"). The shared instance's set of services can now shrink as well as grow, but only by this explicit command, never by an `up`.
- The shared instance now gets reloads that remove processes. Each one removes only processes devtrees has already stopped, and never edits a kept one.
- **The shared lock can be held for a bounded stop**, about 30s plus the targets' `shutdown.timeout_seconds` at worst. An `up` from another worktree waits for it about 10s (#240's budget) and then fails `LOCK_CONTENTION`, the same as during a full `down --shared` today.
- **The in-progress window is closed by the lock check above.** Without it, the window was not just a spawn: it was the whole shared health wait plus the spawn, and a teardown during the wait turned that `up` into a misleading `SHARED_SERVICE_DEAD` (`died_while_waiting`). Taking every worktree's lifecycle lock instead was rejected: the teardown would wait on every `up` and `down` in the repo, under the shared lock.
- **Namespaced remedies.** When every drifted or broken shared service is namespaced, `SHARED_DRIFT` and `SHARED_SERVICE_DEAD` name `devtrees down --shared -n <namespace> --force && devtrees up -n …` as `details.remedy` (the same `up`, with its own namespaces). An always-on service, a port conflict, or a shared instance with no recorded state keeps the full `devtrees down --shared && devtrees up`. **`--force` is in the remedy on purpose.** The service is already drifted or dead for every worktree that uses it. Those worktrees, the caller's own included (and in a busy repo every other app worktree), are exactly the dependants that would refuse an unforced teardown, so without `--force` the remedy would fail `SHARED_IN_USE` on its first run. Two alternatives were rejected. Excluding only the caller's worktree would still trip on the others. Leaving `--force` to a second step would make every agent take two failures to reach the same command. The forced teardown interrupts the worktrees that use these services, which the old full `down --shared` did too, and stops only those namespaces' shared services, never more. It still waits for in-flight commands, as above. A shared service outside the namespaces that depends on one would refuse unforceably, so its namespaces are added to the remedy, transitively. If an always-on one depends on them, only the full teardown can work, and the remedy is the full teardown. Smoke 129 runs the printed remedy verbatim while both worktrees depend on the service, and it succeeds. Release notes: `details.remedy` changed on `SHARED_DRIFT` and `SHARED_SERVICE_DEAD` for namespaced services. Every `details.remedy` this ADR adds is one runnable command, the style ADR-0011 set. `SHARED_IN_USE` gives the `--force` rerun only when every blocker is a real worktree dependant. It gives the plain retry while a command is still in flight, and, for a shared dependant, the teardown that also names its namespaces. `SHARED_REMOVAL_FAILED` gives the retry. The message carries the alternatives, including that a full teardown stops the shared instance for every worktree.
- **New codes, additive under ADR-0005:** `SHARED_IN_USE` (`details: {namespaces, services, dependants, forceable, remedy}`) and `SHARED_REMOVAL_FAILED` (`details: {services, reason, config_path, remedy}`). The `down` envelope for `--shared -n` adds `namespaces`, `services`, `removed` (what left the instance, leftovers included), `inactive_namespaces`, `instance_stopped` and `forced_dependants` (the dependants `--force` overrode) to the plain `down --shared` keys; there `stopped` means something running was stopped, and `down --dry-run` emits `down_dry_run`. The worktree derived config gains `x-devtrees.shared_depends_on`. No `schema_version` bump.

## Considered Options

- **Let the reload stop the targets** (one step, no bounded stop): process-compose's update has no SIGKILL escalation, so a `shutdown.command` that does not stop its process would hang the reload, and the shared lock with it (#188, ADR-0009).
- **Reference-count the shared services** so the teardown knows who uses them: rejected by ADR-0001. Reading each live worktree's recorded edges answers the same question from state that already exists, without a counter that drifts when a worktree dies uncleanly.
- **Fail on a namespace with nothing to stop:** see point 2. It would make the command non-idempotent and still could not catch a typo reliably.
- **Keep the removed services' ports in `shared-state.json`:** see point 7.
- **Let `--force` override a shared dependant** by also stripping the edge from the kept service: that edits a running shared service's config, so process-compose restarts it.
