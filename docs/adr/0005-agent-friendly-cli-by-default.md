# Agent-friendly CLI by default

Coding agents are a first-class user of devtrees alongside human developers. Rather than gate agent ergonomics behind a mode flag, the CLI degrades gracefully based on context: `devtrees up` auto-detects TTY and skips TUI attachment when none is present, every command that emits structured data accepts a global `--json` flag, and new commands (`devtrees env`, `devtrees logs`) cover the gaps that the TUI-first surface left for non-interactive operators.

## Considered Options

Two choices in this surface are worth recording because a future contributor will see them and want to "fix" them:

- **`--json` errors are emitted on stdout, not stderr.** The Unix idiom is errors on stderr, but `--json` is an agent-facing contract: the agent reads one stream, parses one document, branches on `error.code`. Stderr stays available for human-readable diagnostics; the structured envelope (`{"error": {"code", "message", "details"}}`) is always on stdout when `--json` is set. The alternative (errors on stderr) forces agents to capture and merge two streams to handle failure.

- **`devtrees up` leaves the stack running when health-wait times out.** The atomic alternative (tear down on failure) gives cleaner semantics but destroys the debug surface — the agent loses access to the logs of *why* startup failed. Leaving the stack up means `devtrees logs <service>` and `devtrees ls --json` still work after a `HEALTH_TIMEOUT` exit, and the agent can decide whether to retry, debug, or `down`. Default timeout is 120s, overridable with `--wait-timeout`.

- **The silent health-wait (and `HEALTH_TIMEOUT`) is the *headless* path's readiness gate; the attach path renders readiness live instead (#132).** On `--json` / `--no-attach`, nothing renders process state, so `up` polls the instance silently until every service is healthy and only then returns — that gate is what turns "up returned" into "the stack is serving traffic". On the attach path (a TTY, or explicit `--attach`), `up` attaches the `process-compose` TUI *immediately* after starting the server detached: the human watches services transition starting → ready live, so the TUI **is** both the progress indicator and the readiness signal, and `up` returns when they detach. Attaching after a silent wait was the obvious-looking alternative, but it leaves a slow stack (e.g. a 30–60s cold Supabase) painting a blank terminal for the whole wait, which reads as a hang. The consequence is deliberate: in attach mode `up` returning no longer implies the stack is healthy (the human decides that by watching), and `HEALTH_TIMEOUT` cannot fire — it has no meaning when a human is at the wheel.

## Consequences

- The CLI has no "agent mode" — behavior is driven by TTY detection and explicit flags. This keeps the human-facing surface unchanged and avoids a flag the agent must remember to set on every invocation.
- `--json` output shapes are a stable contract **once devtrees declares the agent surface stable** (target: `v0.1.0` / first published agent release). Until then, the project is in walking-skeleton mode and shape changes don't require a `schema_version` bump — `"1"` is a placeholder for "draft v1, expect breaking changes." Once the surface is declared stable, the first real consumer migration becomes the trigger for `schema_version: "2"`, and subsequent breaking changes require a bump. While pre-stable, breaking changes are documented in CHANGELOG / release notes, not the version field — this keeps the version field a faithful signal that a real migration is required whenever it changes.
- Error codes (`PROCESS_COMPOSE_NOT_FOUND`, `CONFIG_INVALID`, `LOCK_CONTENTION`, `HEALTH_TIMEOUT`, `CONFIG_DRIFT`, `SHARED_DRIFT`, `STALE_PORT_BLOCK`, `INSTANCE_NOT_FOUND`, …) are part of that contract; new codes are additive, renames are breaking. `STALE_PORT_BLOCK` (#58) is the stale-child detection envelope `up` emits when foreign processes hold the worktree's declared named ports at start time — it complements the allocator's intentional non-re-probing (stability-first fast-path returns the registry-recorded block verbatim, so without this pre-flight the orphan listener would silently win EADDRINUSE against the new service). Its `details.collisions[]` lists each `{port_name, port, pid, command}` so an agent can kill the orphans and retry without guesswork. `SHARED_DRIFT` (#83) is the shared-tier counterpart of `CONFIG_DRIFT`: the running shared instance persists its name→port map and a hash of the shared subset it was started from; `up`/`env` from a worktree whose shared subset diverges (a branch added, removed, or edited a shared service) fail with this envelope instead of silently injecting port numbers the instance never bound. Remediation is `devtrees down --shared && devtrees up`, which restarts shared from that worktree's config and re-persists the map. Pure reordering never trips it — the hash is order-insensitive and injected numbers come from the persisted map. `SHARED_START_FAILED` (#92) is the lazy-start failure envelope: the shared spawn is fire-and-forget, so an instance that crashes before binding its control socket is only observable as the socket never appearing — `up` fails with this code (details carry `socket_path`, `config_path` and `timeout_ms`) instead of reporting `shared_started: true` for a dead instance. `config_path` was added with #157's follow-up — the remediation used to print a literal `<shared config>` placeholder, so the one command it told you to run could not be run; additive under this same policy, no `schema_version` bump. `WORKTREE_START_FAILED` (#157) is the same failure for the *worktree* instance, and exists because one code could not name two instances: both instances are spawned fire-and-forget and both are only observable as "the socket never appeared", but they are torn down by different commands (`devtrees down` vs `devtrees down --shared`) and debugged against different derived configs. The worktree wait originally threw `SHARED_START_FAILED`, so a stack declaring no shared tier at all failed with a shared-instance envelope pointing at its own socket — issue #154 was diagnosed against a shared instance that did not exist. Reusing one code with caller-aware prose was rejected: agents branch on `error.code`, so the distinction has to live there rather than in a message they would have to parse. Additive, so no `schema_version` bump — same treatment `SOCKET_PATH_TOO_LONG` got in ADR-0007. `details` carries `{worktree_id, socket_path, config_path, timeout_ms}`; `config_path` is the file to run by hand, which the shared envelope's advice named wrongly for this caller (it pointed at the shared config) before either envelope carried a real path. `PROCESS_COMPOSE_TOO_OLD` (#173) is `up`'s pre-flight failure when the installed process-compose is below the supported minimum (v1.122.0, the first release accepting a list-valued `namespace`): it is checked with one `process-compose version --short` before any port is allocated or anything is spawned, and `details` carries `{installed_version, minimum_version, upgrade_url}` (`installed_version` is `null` when the output could not be parsed). Additive, so no `schema_version` bump. `SERVICE_NOT_FOUND` (#109) is `logs`' fail-fast envelope for a service name absent from the target instance's derived config: `process-compose process logs <unknown>` blocks forever instead of erroring, so `logs` validates the name against the instance (worktree or `--shared`) before streaming and fails with this code — `details` carries `{service, valid_services[]}` so an agent can correct the name without a second round-trip. `CONFIG_DRIFT` gained `details.reason` (#188), additive with no `schema_version` bump. The reason is `not_supported` or `error` when process-compose refused the hot-reload: the instance is untouched, and `devtrees down && devtrees up` applies the new config. It is `timeout` when the config reload did not finish within its budget because a changed service's old process never stopped. Typical causes are a `shutdown.command` that exits 0 without stopping the process, or a process that ignores SIGTERM and has no `shutdown.timeout_seconds`. In that state a retried `up` would make process-compose start a second, untracked copy. The remediation is to kill the old process, wait for it to exit, then run `up` again to resync. `down` also stops it (#206): process-compose no longer lists the old process, but the pending-reload marker below records it, and the bounded stop (#190) force-kills it before stopping the instance. Agents branch on the reason rather than parse the prose. `reload_pending` (#191) is the guard on that state, additive like the rest: a retried `up` refuses before reloading while an earlier timed-out reload is still pending, because process-compose does not serialise config updates and a second one would start an untracked copy of the service. `details` adds `services` (the stuck services) and `pids` (their old processes still alive; empty when the old process has exited but process-compose has not brought the service back yet). Detection is a per-worktree marker written under the lifecycle lock when a reload times out (the changed services and their pre-reload PIDs), cleared once a read shows those PIDs gone and the services back, and by `down` and a fresh start. There is deliberately no stateless fallback that reads the project's shape against the on-disk config: after a timed-out rename or removal that config is stale, and `up -n` on a namespace with no services boots an empty project legitimately (#176), so each version of it refused healthy instances. It would only have covered timeouts from builds without the marker, and none was released. A timeout also invalidates the stored hash, so the first `up` after the pending reload converges re-applies whatever `devtrees.yaml` says then, even if it was reverted meanwhile. The marker is anchor state, like the stored hash: it records what devtrees did, and the live project is still what it is checked against. `NAMESPACE_NOT_RUNNING` and `SHARED_SERVICE_DEAD` (#177) are `up`'s verdicts on an already-running instance (ADR-0008): the first for an `-n` naming a namespace the instance was not booted with (`details` carries `{worktree_id, namespaces, services, remedy}`), the second for a dead service in the shared instance (`details` carries `{dead_services[], remedy}`). A dead *isolated* service is not a new code: since #178 `up` restarts it, and one that stays dead or never becomes healthy is `HEALTH_TIMEOUT`, with the same `dead_services` and `remedy` details, because its remedy is the same worktree `down` + `up` a stuck start gets. The shared case gets its own code for the reason `WORKTREE_START_FAILED` was split from `SHARED_START_FAILED`: its remedy tears down a different instance (`devtrees down --shared`), and agents branch on `error.code`, not on prose. Both additive, no `schema_version` bump. `SERVICE_START_FAILED` (#178) is the one case of that restart with a code of its own: process-compose refused or errored on the `process start` request itself, so there is no run to wait on. `details` carries `{worktree_id, services[], remedy}`: each refused service as `{name, message}` with process-compose's own complaint, and the worktree `down` + `up` that restarts the stack. A refusal because the service is already running is not a failure: another `up`, or the service's restart policy, got there first. The restart runs under the worktree's lifecycle lock, which the worktree `down` now also holds. An `up` that finds, under that lock, that a concurrent `down` stopped the instance starts nothing and fails with the existing `INSTANCE_NOT_FOUND`, which is the state it found. The `up` success envelope gained `restarted[]`, the services that this `up` started; a service process-compose reported as already running is not included. Both additive, no `schema_version` bump. `INSTANCE_UNRESPONSIVE` (#186) is what `up` and `down` (worktree or `--shared`) fail with when an instance's control socket exists but its liveness probe never gives a definitive answer. The probe treats only a connect as live. It treats only `ENOENT`, `ENOTSOCK` (a plain file at the path, which no process can be listening on), or an `ECONNREFUSED` with no process holding the socket as stale, and only stale licenses unlinking the socket file. Everything else is *unknown* and is retried with backoff. That covers a connect timeout, and an `ECONNREFUSED` while a process still holds the socket (on macOS a listener with a full accept backlog, such as a frozen process-compose, refuses connects). It covers an `lsof` holder check that itself times out, and any other error, including the `EAGAIN` Linux reports for a full backlog. `INSTANCE_NOT_FOUND` was rejected because it states the opposite of what is known: the instance may well be running, and reporting it as gone is exactly the bug (`down` said "nothing running" while the services kept their ports). Taking the fresh-start path was rejected for the same reason: it would collide on the live instance's ports. `LOCK_CONTENTION` was rejected because no lock is involved. `details` carries `{instance, socket_path, attempts, remedy}`; `instance` is the worktree id or `shared`. Nothing is started or stopped, and the socket is kept. `ls` does not fail on it: it lists the instance with `status: "unknown"`. `prune` does not unlink an unknown orphan blindly either. It sends the orphan the graceful `process-compose down` a running one gets. If that fails, it keeps the orphan's socket, derived config and registry entry and reports it under the new `prune.unreclaimed[]` (`{id, kind, worktreePath, socketPath, message}`), never under `pruned[]`, so a later `prune` can retry. Additive, no `schema_version` bump. `DOWN_TIMEOUT` (#190) is what `down` (worktree or `--shared`) fails with when process-compose cannot finish stopping. process-compose v1.122.0 never escalates to SIGKILL for a `shutdown.command` that exits 0 without stopping its process, or for a process that ignores SIGTERM and declares no `shutdown.timeout_seconds`, so its `down` used to block forever. devtrees now snapshots each service's pid (`process list`, then `ps`) before the stop and bounds `process-compose down` at 30s plus every `shutdown.timeout_seconds` in the derived config, as the reload is bounded (#188). On expiry it SIGKILLs, by process group, only the snapshot service processes that are still alive and still the same process (same parent, process group and command line, so a reused pid is never hit). process-compose then sees them exit and finishes its own shutdown. The old processes a timed-out hot-reload left behind (#206) are handled before the stop instead, and never during it. process-compose applies a reload's updates one service at a time; each update stops the old run, waits for it to exit, then starts the new copy without checking whether a shutdown has begun. So any new copy that starts after `process-compose down` has fixed its shutdown order is never stopped and outlives process-compose as a PPID-1 orphan. The rule is therefore: devtrees never kills a pending old run once the stop has begun, and never begins the stop while the update is still in flight. Before the stop it waits for the update to finish, polling `process list`, and kills only the stuck old runs: those process-compose no longer lists but still waits on. process-compose drops a service from the list the moment its update begins, so an unlisted old run may just be part-way through a slow graceful stop; it counts as stuck only once it has stayed unlisted for a grace period, the `down` budget (the patience the stop's own escalation gives any process), measured from when `down` first saw it unlisted or, when `up` already saw it unlisted as the reload timed out, from then (the marker's `unlistedAt`). Each poll re-checks, because the updates run one at a time: when one stuck run is killed, process-compose moves on to the next changed service, whose old run may be stuck too (a shared env var changes every service). The wait is extended to cover each stuck run's grace period plus the time for its new copy to start, and is still bounded, since every old run extends it at most twice. An old run it still lists belongs to an update that is only queued, so it is left alone and process-compose stops it, `shutdown.command` included, when it reaches it. process-compose runs without `--keep-project`, so it exits once nothing is running, for instance when the new copy fails to start (an orphan whose worktree is gone); `down` then stops waiting, runs no `process-compose down`, and cleans up as for a dead supervisor, so `down` and `prune` succeed in one pass. The stuck runs come from the pending-reload marker, which records each one's parent, process group and command line when the reload times out. They are killed only while all three still match and the parent is this instance's process-compose; an entry without that identity is never killed, since on the pid alone it could be a running `shutdown.command`. The `ps` read behind that check is retried when it comes back empty or without the supervisor, both when the marker is written and before the stop, so one failed read under load does not leave the run unverified. devtrees then waits (the `down` budget, at least 5s) until every old run has exited or been replaced and every service the update brings back is listed again, and only then stops the instance, new copies included, in the normal way. If the update does not finish in that time (an old run devtrees could not verify, an unreadable `process list`, a slow update), `down` does not start the stop at all and fails with `DOWN_TIMEOUT`, with `details.pending_reload` naming the services still being applied, `stuck_services` the old runs it still waits on, and `remedy` leading with the old processes to kill by hand (safe because no stop is running), naming any devtrees could not verify (no recorded identity, or one that no longer matches), or saying that `process list` could not be read at all. Stopping process-compose by hand does not help there: its own shutdown waits on the same old process. The wait holds the worktree's lifecycle lock, so a concurrent `up` can fail `LOCK_CONTENTION` meanwhile. The escalation at the budget's expiry used to kill such runs too, as a backstop; it was dropped, because that kill lands exactly in the window that starts an orphan, and a loud `DOWN_TIMEOUT` is better than a silent orphan behind a successful exit. A stop that needed this still succeeds, and reports every killed process in the new `force_killed` (`[{service, pid}]`, always present) on the `down` envelope and on each `prune.pruned[]` row, plus a stderr warning in human mode. Only when process-compose still has not exited after a further 10s does `down` fail with `DOWN_TIMEOUT`. `details` carries `{instance, socket_path, timeout_ms, process_compose_pid, stuck_services, force_killed, remedy}`, plus `pending_reload` when the stop was not begun because of a pending reload. The socket and derived config are kept, so `ls` still sees the instance and a retry can finish. devtrees never kills process-compose itself, nor a running `shutdown.command`: that would skip the hooks it has not run yet, and those are what clean up containers and other out-of-band resources. The remedy hands that decision to the operator, naming the pid. After process-compose is gone, a worktree `down` runs the shutdown hooks itself through the dead-supervisor reap (#148); a `down --shared` only cleans up. `UNKNOWN` was rejected because agents need to tell "retry, or escalate to a human" apart from an unclassified failure. `INSTANCE_UNRESPONSIVE` was rejected because process-compose did answer and did start shutting down. Prune's orphan stop is bounded the same way, and an orphan whose stop times out is reported under `prune.unreclaimed[]` with its state kept, whatever its probed liveness, because the timeout proves its process-compose is still running. Additive, no `schema_version` bump. `DOWN_INCOMPLETE` (#155) is what a worktree `down` fails with when process-compose did stop but something the instance started is still alive. process-compose calls a service stopped once its direct child exits, and it skips the `shutdown.command` of a process it does not consider running, such as a daemon whose launch exited non-zero after starting containers. So `down` used to report "worktree instance stopped" and exit 0 while a SIGTERM-ignoring grandchild or a container kept the port, and with the socket gone nothing pointed at them any more. Now the bounded stop also records each service's descendants and process-group members, and once process-compose has stopped gives the leftovers a 5s grace, then SIGKILLs them (reported in `force_killed`); the pending-reload rule stands, as a pending old run is a child of process-compose, not of a recorded service. `down` then runs the skipped daemon hooks itself, and connects to each named port of the services it had booted. A port that still accepts a connection, or a descendant SIGKILL could not stop, fails with this code. `details` carries `{instance, survivors[], force_killed, remedy}`, each survivor `{service, pid, command, port_name?, port?}`. Reusing `DOWN_TIMEOUT` was rejected because the stop did finish and its remedy (stop process-compose by hand) does not apply. A warning on a successful exit was rejected because that is the false success being fixed. The derived config and port block are kept, so the retry the remedy names, a second `down`, runs every shutdown hook through the dead-supervisor reap. `STALE_PORT_BLOCK` collisions gained `accepts_connections` in the same change. A holder that refuses a TCP connect, such as a container runtime's stale port forward (one process serving every instance, never to be killed), cannot answer the new service's traffic, so it no longer fails `up` alone: `up` warns about it and goes on. If it does block the service's bind, the service fails loudly. Both additive, no `schema_version` bump.
