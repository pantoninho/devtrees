# Per-service and per-namespace lifecycle control (`stop`, `restart`)

Every lifecycle verb devtrees had acted on a whole instance. Cycling one process meant `down` + `up`, which in the reporting stack also tore down Supabase's containers and the backend to bring back one Metro server, or reaching past the CLI into the process-compose socket (#160). A consumer that boots `-n app -n ios` and wants to give the simulator back while the backend keeps serving had the same problem one level up (#171). Namespaces bought selective boot but not selective stop. This ADR adds the two verbs that close the gap, `stop` and `restart`, and decides what they promise, because process-compose cannot tell devtrees whether a process was stopped on purpose or crashed.

## The contract

**Two new top-level verbs, `devtrees stop` and `devtrees restart`.** Each takes one or more service names and/or a repeatable `-n/--namespace <namespace>`, which expands to every isolated service in that namespace (a service in several namespaces is in the expansion if _any_ of them is named, as for `up`). Several names are processed one after another, in `depends_on` order, because `process start`, `process restart` and `namespace start|stop|restart` take exactly one target in process-compose v1.122.0 (only `process stop` accepts several), so devtrees loops. They act on this worktree's instance only. _Removed: see the amendment "`stop` removed"._

**There is deliberately no `start`.** A stopped service comes back through `up`, which already restarts dead or stopped isolated services in the namespaces it covers (ADR-0008, reconcile). A separate `start` would be a second path that could disagree with `up`. In particular it would bring a service back on stale config by skipping the pending hot-reload, and `process start X` does not start stopped dependencies: a dependent with a `process_healthy` condition becomes `Skipped` and never runs. `up` orders by `depends_on`; that is why it is the bring-back path.

**A stop does not survive the next `up`.** process-compose reports a stopped process exactly like a crashed one: `Completed` with `exit_code -1`, the same as a SIGKILLed or externally SIGTERMed process (verified on v1.122.0; a finished one-shot shows `exit_code 0`). Telling "stopped on purpose" from "crashed" would need devtrees to record it, and ADR-0008 rejected persisting a second source of truth that can disagree with what is running. So the next `up` covering that namespace restarts the service, and `stop`'s output and the docs say so. `stop -n <namespace>` is transient in the same way; it expands to the namespace's isolated services and stops them as `stop <service...>` does (amended by #224, below). _Removed: see the amendment "`stop` removed"._

**`restart` restarts what it names, and only that.** `restart X` does not cascade to dependents, matching process-compose (`process restart` does not restart them). A consumer that wants dependents cycled names them.

**Bare `restart` restarts every booted isolated service in place**, in `depends_on` order. Ports, the instance id and connections are kept, shared services are untouched, and namespaces that were not booted stay unbooted (the booted set is read back from the project, as in ADR-0008). _Not in effect: the fallback below applies, and a bare `restart` fails `INVALID_ARGS` (amendment #225)._ Bare `stop` with no arguments fails `INVALID_ARGS` and points to `down`. A `-n` that expands to no isolated service fails `NO_SERVICES_SELECTED`, as for `up`. A clean slate is still `down` then `up`. _Removed: see the amendment "`stop` removed"._

**Idempotent.** Stopping an already-stopped service succeeds, and restarting a stopped service succeeds. Validation happens before anything is touched, in this order: no running instance fails `INSTANCE_NOT_FOUND`; the declared services are read from the running instance's derived config (not `devtrees.yaml`, which may have changed since); a shared service fails `SHARED_SERVICE_REFUSED` (below); an unknown service name fails `SERVICE_NOT_FOUND` (the existing `logs` code, ADR-0005, with the same `details` of `{service, valid_services[]}`, listing the derived config's services); a hot-reload still pending fails `CONFIG_DRIFT` with `reason: reload_pending`, exactly as `up` refuses (#191), because the pending update starts the new copy when it finishes and would undo the verb; and a named service whose namespace the instance did not boot, like a `-n` naming such a namespace, fails `NAMESPACE_NOT_RUNNING` with ADR-0008's `details` of `{worktree_id, namespaces, services, remedy}`, the remedy being the `down` + `up` that boots the booted namespaces plus the needed ones. A named service that is not running is not an unbooted one: it was booted and has stopped, so `stop` succeeds and `restart` starts it. _Removed: `stop` no longer exists; see the amendment "`stop` removed". The checks stand for `restart`, and its `reload_pending` refusal has its own reason: the pending update is waiting on the old run, and a run restarted now is one it does not know about and would wait on forever._

**Shared services are refused with a named error.** Naming a shared service (per `devtrees.yaml`, tolerated when it is broken, or the shared instance's derived config) fails `SHARED_SERVICE_REFUSED` with `details` of `{services, remedy}`, the remedy being `devtrees down --shared && devtrees up`; a `-n` expansion contains isolated services only. Per ADR-0008, a worktree-scoped command must not bounce a repo-wide process (ADR-0001). A `--shared` flag is deferred.

### `restart` has `up` semantics for success

`restart` waits for the named services to be healthy and honours `--wait-timeout`. A service that does not become healthy fails `HEALTH_TIMEOUT` and is left running, so `logs` and `ls --json` still work afterwards (ADR-0005). `SERVICE_START_FAILED` is for process-compose refusing the restart request itself, as in ADR-0008. `--json` emits the usual envelope.

### `stop` waits for actual exit

`stop` is not done when process-compose accepts the request; it is done when the process is gone. It reuses `down`'s bounded-stop machinery (ADR-0005; #190, #208, #219). `process stop` signals the whole process group and escalates to SIGKILL after `shutdown.timeout_seconds`, but a process that calls `setsid()` escapes the group, and a `shutdown.command` that exits without stopping its process leaves the service `Terminating` forever. So `stop` allows the grace period (including the hook time limit), then force-kills what is left of the service's process group, reports it in `force_killed` (`[{service, pid}]`, as on `down`), and fails `SERVICE_STOP_INCOMPLETE` if a process still outlives that, with `details` naming it, mirroring `DOWN_INCOMPLETE`. _Removed: `stop` no longer exists; see the amendment "`stop` removed" below. The bounded stop lives on as the first half of `restart`._

### `stop` refuses a service that has not started

A service still `Pending`, waiting on its dependencies, has no process to stop. process-compose v1.122.0 nevertheless accepts `process stop` for it and leaves it `Terminating` with no process for good: it never starts, not even once its dependency is healthy, and `up` cannot bring it back, which would break the transient-stop promise above. So `stop` fails `SERVICE_PENDING` before asking process-compose anything, with `details` of `{services, waiting_on, remedy}`: wait until it starts, or stop what it waits on. _`stop` is removed (see the amendment "`stop` removed"); `restart` keeps this refusal._

### `stop` refuses to stop the last running processes

process-compose v1.122.0 exits ("Project completed") when every process has stopped, unless booted with `--keep-project`. A `stop` that took the last running process would therefore silently `down` the instance, losing its socket and its debug surface under a command that promised only a service. So `stop` fails `LAST_SERVICES_RUNNING` if the stop would leave the instance with no running process, naming the services and pointing to `down`. The check is conservative: only a process running now counts (process-compose's `is_running`). Done one-shots and already-stopped services do not count, and neither does a `Pending` service: it may be waiting on the very service being stopped, and then never starts. If process-compose exits during a stop anyway (something else stopped meanwhile), `stop` fails `INSTANCE_NOT_FOUND` at once instead of reporting the services stopped. _`stop` is removed (see the amendment "`stop` removed"); `restart` keeps this refusal._

### `ls` shows what is running

Acting on one service needs seeing it (#160 ask 3). `ls` gains a NAMESPACES column (booted namespaces, read back from the project as in ADR-0008) and a `--services` flag that prints one row per service. `ls --json` gains a `services[]` list per instance: `name`, `namespaces`, `tier` (`isolated` or `shared`), `status` (`active`, `dead` or `done`, from the existing dead-versus-done classification of ADR-0008) and `pid`. Additive.

As built (#226): `services[]` already existed on `ls --json` (and on `up --json`) with `status` holding process-compose's own state string (`Running`, `Completed`), so the classification is published as `state` rather than `status`, keeping the change additive and the two envelopes' rows alike; the human `--services` column is headed STATE to match. `pid` is `null` unless process-compose reports the process running (`is_running`): a dead or done row, and a `Restarting` one in its backoff, keep the pid of a run that has ended. Each instance's read is bounded at 5s (`readStatusesWithin`, as for `up --dry-run`) and the instances are read in parallel; one that does not answer is listed with `services_read: "unresponsive"` (`"ok"` when read, `"skipped"` when stale or of unknown liveness, including one found gone mid-read) and `?` in human output, never failing `ls`. `namespaces` is `null` when not known (no answer, or the derived config is gone). A pending reload's services count as booted while its marker is on disk (ADR-0005, #191), surfaced as `reload_pending`.

## Considered Options

- **Persistent `down -n <namespace>`** (#171): deferred. It is implementable by hot-reloading a derived config without the namespace: process-compose removes the processes, the read-back then reports the namespace as unbooted, and re-adding works only for namespaces in the boot `-n` set. But every later reload would have to filter to the currently booted namespaces, or an edit to `devtrees.yaml` revives the downed one. It would also partly reverse ADR-0008's "adding a namespace is not supported". The cost and risk are not worth paying until a consumer needs it. #171 stays open; the transient `stop -n` covers the immediate need (give the simulator back; the next `up` that covers it brings it back).
- **A one-run launch override** (#160 ask 2, e.g. `restart mobile -- --clear`): deferred. process-compose has no per-start args. `POST /process` (UpdateProcess) replaces one process's config and restarts only it, but the override is sticky: it survives `process restart`, is invisible to devtrees' stack hash and drift detection, and is reverted by the next drift reload. Devtrees would have to record and revert it itself, which is state it does not keep today.
- **A `start` verb**: rejected, for the reasons above. It can be revisited if someone needs "bring back exactly this one service without reconciling the rest".
- **Recording intentionally stopped services**, so `up` leaves them stopped: rejected. It is the same second-source-of-truth argument ADR-0008 made against persisting the booted selection.
- **Bare `restart` as `down` + `up`**: rejected in favour of in place. It is faster and keeps ports and the instance alive. If in-place restart of the whole booted set proves too hard to do correctly, the fallback is that bare `restart` fails with a clear error for now.
- **Cascading restarts to dependents**: rejected. It matches process-compose, keeps `restart X` meaning X, and a dependent that must be cycled can be named.
- **Booting with process-compose `--keep-project`** so the last `stop` is allowed: deferred. It changes boot semantics and interacts with #203's empty-selection exit. `LAST_SERVICES_RUNNING` is the cheap guard.
- **Restart or stop shared services from a worktree**: rejected, per ADR-0008; `--shared` is deferred.

## Consequences

- **A stopped service is only stopped until the next `up`.** Anyone expecting `stop` to mean "keep it off for the session" will be surprised; `stop`'s output and the README say so. A script that wants it off must not call `up` on that namespace. _Removed: see the amendment "`stop` removed"._
- **New error codes, additive under ADR-0005** (no `schema_version` bump): `SHARED_SERVICE_REFUSED` (a shared service was named), `LAST_SERVICES_RUNNING` (the stop would leave no running process; `details` names the services and the `down` remedy), `SERVICE_STOP_INCOMPLETE` (a process outlived the bounded stop and the force-kill), `SERVICE_PENDING` (a named service is still waiting on its dependencies, so there is nothing to stop). `SERVICE_NOT_FOUND` is reused from `logs`, and `INVALID_ARGS` and `NO_SERVICES_SELECTED` are reused for a bare `stop` and an empty `-n` expansion. Agents branch on `error.code`, so each distinction lives in a code rather than prose. The names are proposals for the implementer to confirm. _`SERVICE_STOP_INCOMPLETE` was removed with `stop` (amendment "`stop` removed"); the other codes remain, emitted by `restart`._
- **`ls --json` is extended additively**: a `services[]` list and a `namespaces` field per instance.
- **The README and `--help` need the new verbs**, the transient-stop caveat, and the error codes table.
- **The implementation reuses `down`'s bounded stop and `up`'s reconcile and health wait**; neither is a new mechanism, which keeps one definition of "stopped" and of "healthy".
- **`stop` can never end an instance**; `down` remains the only verb that does, apart from `prune`. _Removed: see the amendment "`stop` removed"._

## Amendment (#222)

A named service that the running instance did not boot (its namespace was not selected) fails `NAMESPACE_NOT_RUNNING` for `stop` and `restart` alike, with ADR-0008's details `{worktree_id, namespaces, services, remedy}`, the remedy booting the running namespaces plus the needed ones; names are checked against the running instance's derived config, and a pending hot-reload refuses with `CONFIG_DRIFT` (`reload_pending`) as `up` does.

Restarting the instance's last running process(es) is refused with `LAST_SERVICES_RUNNING` (`details: {worktree_id, services, remedy}`, the remedy a `down` + `up` with the booted namespaces), before anything is touched. `restart` stops a service with `stop`'s bounded stop before starting it, and process-compose v1.122.0 exits once nothing runs. Its own `process restart`, which keeps the project alive, starts the new run after about 1s whether or not the old run has exited, so a server still draining loses its port: the new run dies (and the instance with it) or comes up on another port. Booting with `--keep-project` is the deferred alternative, as for `stop`.

## Amendment (#224)

`-n <namespace>` on `stop` and `restart` is an expansion step, not a separate path. Each `-n` (repeatable) adds every isolated service of the running instance's derived config that is in that namespace (a list-valued `namespace:` puts a service in each of its namespaces, as for `up`). The union with the named services, each once, then goes through `resolveNamedServices` and the existing stop and restart unchanged: the same order of checks, `SERVICE_PENDING`, `LAST_SERVICES_RUNNING`, `reload_pending`, the bounded stop and restart, and `depends_on` order. Neither verb uses process-compose's `namespace stop|restart`, which would bypass the bounded stop, the last-process guard and the health wait.

- A `-n` namespace with no isolated service in the derived config fails `NO_SERVICES_SELECTED` (`details: {worktree_id, selected_namespaces, namespaces}`, `selected_namespaces` naming the empty ones), checked after the shared and unknown-name checks and before `reload_pending`. Each `-n` is checked on its own, so a typo next to a valid namespace is not silently ignored.
- A namespace the instance did not boot needs no new check: its services are absent from the project, so the existing check fails `NAMESPACE_NOT_RUNNING` with the same details and remedy.
- Shared services are never in the expansion. They are skipped and reported in `skipped_shared` (in both envelopes, and a line of human output); naming one explicitly is still `SHARED_SERVICE_REFUSED`. A shared service cannot declare a `namespace:` (`CONFIG_INVALID`), so it is in the implicit `default` namespace, and only `-n default` skips any.
- `stop -n` is transient like `stop`: the next `up` that covers the namespace (`up -n <namespace>` on the running instance) brings its services back. The persistent `down -n` stays deferred (#171). _Removed: see the amendment "`stop` removed"._

## Amendment (#225): bare `restart` falls back to `INVALID_ARGS`

The fallback this ADR allowed for is in effect. A bare `devtrees restart`, with no names and no `-n`, fails `INVALID_ARGS` before anything is touched. The message says to name the services or namespaces (`devtrees restart <service...>`, `devtrees restart -n <namespace>`), or to run `details.remedy`: the `down` + `up` that boots the namespaces running now, spelled by `formatUpCommand` from the booted set read back from the project (ADR-0008). When the running namespaces cannot be read (no running instance, or one that does not answer), the remedy boots every namespace the instance's derived config declares (or `devtrees.yaml`'s isolated services, when there is no derived config), and the message says so. A plain `devtrees up` there could silently drop a booted namespace, or select nothing (`NO_SERVICES_SELECTED`) in a stack whose services all declare one. The refusal reads the instance but takes no lock, leaves a stale socket file in place, and never fails with another code.

The reason is the instance's last running process. Restarting the booted services one at a time with `stop`'s bounded stop and a start works while another process keeps running. On a one-service instance, or one whose other services are finished one-shots, the last restart has to stop the only running process, and process-compose v1.122.0 exits once nothing runs. A partial bare `restart` that skips that service would not be "restart everything", so it was not built. `restart -n <namespace>` (#224) is no way around this either: it expands to the namespace's isolated services and goes through the same resolver and the same per-service `LAST_SERVICES_RUNNING` refusal, so it restarts the namespace in place one service at a time and refuses a step whose service is then the instance's only running process. Checked against v1.122.0. Smoke scenario 107 pins the `process restart` result, and scenarios 108 and 109 pin the two `POST /process` results; the others were checked by hand and in review:

- **Ordering** cannot help: on a one-service instance there is nothing else to keep running.
- **`process stop` then an immediate `process start`**: unsafe. process-compose exits when the old run ends, whether or not a start lands. The start is refused ("already running") while the old run drains; a client retrying it in a tight loop sometimes never got one in (92 attempts over a 4s drain), and in review a start was accepted (HTTP 200, about 3.03s in) in 2 of 3 runs and process-compose exited anyway, with nothing serving.
- **`process restart`**: process-compose holds the project open for it (`restartCalls`), but it starts the new run after about 1s whether or not the old one has exited. A server that drains for 3s on SIGTERM keeps its port, the new run fails to bind, and process-compose then exits (scenario 107). This is the amendment for #222 again.
- **`POST /process` (UpdateProcess) with the service's own config**: process-compose also holds the project open for an update (`updatesInFlight`), and it waits for the old run to exit before starting the new one, so an exec'd draining server restarts cleanly on its port. But it is not safe in general. (1) It waits only for the process it started: under a shell that does not exec the server, such as `npm run dev`, the shell exits at once, the new run is started while the server still drains, it fails to bind, and process-compose exits (scenario 108). (2) It restarts only because the JSON round trip turns `vars.PC_REPLICA_NUM` from an `int` into a `float64`, which `reflect.DeepEqual` reads as a change. The server keeps the round-tripped config, so the same request a second time restarts nothing (scenario 109), and the next hot-reload restarts that service again even though nothing changed (#194). (3) It has none of `stop`'s escalation: a `shutdown.command` that does not stop the process, or a SIGTERM-ignoring process without `shutdown.timeout_seconds`, leaves the update, and the instance, hanging.
- **A temporary keeper process** added by hot-reload (write a no-op process into the instance's derived config, reload, restart the last service with stop and start, then remove the keeper and reload again) worked by hand with the wrapped draining server. It is rejected because the derived config is the record devtrees reads the running instance from (ADR-0008), and this would edit it twice for every bare restart. An interrupted restart would leave the keeper in the config and the project. The next `up` would not remove it either, because drift is detected from the stored stack hash, which the keeper does not change. The reload also applies whatever else differs between the file and the running project.
- **`POST /namespace/restart/{name}`**: stops every process of the namespace, waits, then starts them, with neither the `restartCalls` nor the `updatesInFlight` guard. On a one-service instance process-compose exited in 2 of 2 runs (in review), leaving the new server orphaned (PPID 1) and holding the port.
- **`process scale`** adds a replica that runs the same command and binds the same port.

Booting with `--keep-project` remains the deferred alternative, as for `stop`. If it lands, a bare `restart` can use `restart`'s per-service stop-then-start for every service, including the last one.

## Amendment: `stop` removed

`devtrees stop` (and `stop -n`) is removed. devtrees keeps a lean CLI, and `stop` did not pay for itself:

- **`restart` covers the cases that matter.** The one thing `up` cannot do is cycle a service that is live but misbehaving; `restart` does that in place.
- **A stop was transient.** process-compose reports a stopped service like a crashed one, so the next `up` covering its namespace brought it back. `stop` promised less than its name suggests.
- **It could not stop the last running service.** process-compose exits once nothing runs, so `stop` refused that case with `LAST_SERVICES_RUNNING` and pointed to `down`.
- **Its motivating case is gone.** Giving a simulator back while the backend keeps serving (#171) no longer applies: simulators moved out of devtrees.

The remaining niche, stopping a service to run it by hand on its port, is possible through `devtrees attach` (the process-compose TUI); the next `up` starts the service again, and `restart <service>` simply starts a stopped one.

What stays: the bounded-stop machinery (`boundedStopServices`, `down`'s escalation, the `SERVICE_PENDING` and `LAST_SERVICES_RUNNING` refusals, the shared resolver `resolveNamedServices` and its `-n` expansion) remains as the first half of `restart`, which is a bounded stop followed by a start. `SERVICE_STOP_INCOMPLETE` is removed: only `stop` raised it (`restart` reports survivors of its stop as a warning and goes on to start the service), and with it the marker that let a retried `stop` re-check the same ports. Every other code this ADR added is still emitted by `restart`.

Pre-1.0, so the removal ships as a breaking minor release (0.3.0).
