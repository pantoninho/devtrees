# `up` converges an instance to declared state; namespaces are opt-in and fixed at boot

> **Amended by [ADR-0010](0010-namespaced-shared-services-and-scoped-drift.md):** a shared service may now declare a namespace, so namespace selection also decides which shared services an `up` uses. The shared instance is still booted without `-n`; it holds the shared services some `up` has selected, and checks for dead shared services cover only the selected ones.
>
> **Amended by #240:** `up` now restarts dead selected **shared** services too, instead of failing `SHARED_SERVICE_DEAD`. A running shared service is still never stopped, restarted or reloaded. See "Reconcile" below.

`devtrees up` used to mean two different things depending on whether the worktree instance was already running. On a fresh start it spawned process-compose and health-waited. On a running instance it compared the stack hash, hot-reloaded on drift, and printed `'<id>' is up.` whatever state the services were in. Two bugs fell out of that split: a dead service in a running instance was never restarted and never reported (#162), and `up -n <new namespace>` on a running instance silently started nothing (#170). Both are the same lie — success reported for a stack that is not what was asked for — and both need one stated contract for `up` rather than two patches. This ADR is that contract. It is implemented by #173 (the v1.122.0 minimum), #174 (health never `ready` when not running), #175 (the stack hash covering every forwarded field), #176 (opt-in namespaces and `NO_SERVICES_SELECTED`), #177 (the running-instance check, fail-loud, and `NAMESPACE_NOT_RUNNING`), #178 (restarting dead isolated services and `SERVICE_START_FAILED`) and #179 (list-valued namespaces and dropped cross-namespace edge warnings).

## The contract

**`up` converges an instance to the declared and selected state, additively.** It never stops anything. Success means every _selected_ service is healthy, on a fresh start and on an already-running instance alike. A running instance that is already converged makes `up` a no-op that still verifies health; a half-dead one makes `up` repair it or fail naming what it could not repair. `is up.` is never printed on the strength of the instance merely existing.

**Namespace selection is exact.** `-n/--namespace` is forwarded verbatim to process-compose, once per value. `-n app` selects `app` and nothing else; it does **not** imply `default`. A consumer that wants both writes `-n default -n app`.

**Namespaces are opt-in.** A fresh bare `up` (no `-n`) starts only `default` — the services that declare no `namespace:`. A service in a named namespace never starts unless that namespace is asked for. If a bare fresh `up`'s `default` selection resolves to zero services, `up` fails with `NO_SERVICES_SELECTED` instead of starting an empty instance and reporting it healthy. `-n` naming only namespaces that have no services is the same error, on a fresh start and on a running instance alike (not `NAMESPACE_NOT_RUNNING`: nothing is missing, nothing is selected). This was first left undecided (#176) and allowed; #203 decided it, because process-compose v1.122.0 exits after any hot-reload of an empty-selection instance and an instance with nothing selected has no use. Only an overall empty selection fails: `-n app -n nope` still starts `app`. There is no "all namespaces" flag; add one if a consumer asks.

**`namespace:` accepts a string or a list**, as process-compose does from v1.122.0. A service in several namespaces is selected if _any_ of them is. A `depends_on` edge from a selected service to an unselected one is dropped by process-compose; devtrees reports the dropped edges rather than letting the dependent start ungated without a trace (the same observability ADR-0003 asks of dropped cross-tier edges).

**The minimum supported process-compose is v1.122.0.** The list form of `namespace:` and the exclusion behaviour below were verified on that version, and devtrees relies on both.

### Bare `up` on a running instance

A running instance has a boot-time selection, and a bare `up` must neither widen nor narrow it. Rather than persist the selection, devtrees reads it back from the instance: **a bare `up` targets the namespaces whose declared services are all present in the process-compose project.** This is exact because process-compose omits `-n`-excluded services from the project entirely (verified on v1.122.0), so "present" means "was selected at boot". The "all present" clause is what keeps it correct when a service belongs to several namespaces: a namespace that only partly appears was not booted, and one of its services being present merely because it also belongs to a booted namespace must not count.

### `up --dry-run` previews the path `up` would take

Because a bare `up` means different things on a fresh and a running instance, a preview that always assumed a fresh start gave the opposite answer to the command it previewed: on a stack with no `default` services, a bare `up --dry-run` against a running instance failed `NO_SERVICES_SELECTED` while the real bare `up` succeeded (#210). So `--dry-run` is instance-aware. When this worktree's instance is running it previews the running-instance path, decided by the same code the real `up` uses: the effective selection read back from the project, whether the stack would be hot-reloaded, which dead selected isolated services would be restarted, and the errors that path raises before acting (`NAMESPACE_NOT_RUNNING`, `CONFIG_DRIFT` with `reload_pending`). Because the real `up` hot-reloads a drifted stack before it reads the selection back, the preview decides against the project as the reload would leave it: services of the new config in the namespaces booted (judged against the config the instance runs now) are present, so a service added to a booted namespace neither narrows a bare selection nor raises `NAMESPACE_NOT_RUNNING`, and a dead service the reload itself restarts is not reported as one `up` would restart. It stays side-effect free: a read-only liveness probe and one `process list` read (capped at 5s, or `--wait-timeout`, so a slow or frozen process-compose fails `HEALTH_TIMEOUT` sooner than in the real `up`), no lock, no reload, no restart, no state or marker written. The `up_dry_run` envelope says which path it previewed (`instance: "fresh" | "running"`). It cannot preview the outcome of the side effects themselves — a refused reload or restart, or a service that never becomes healthy.

### Adding a namespace to a running instance is not supported

process-compose has no runtime way to widen the selection. `namespace start` reports "not found" for an excluded namespace, and `project update -n` ignores namespaces that `-n` excluded at boot (both verified on v1.122.0). So `up -n <namespace that was not booted>` on a running instance fails with `NAMESPACE_NOT_RUNNING`, names the namespaces, and tells the caller to `down` then `up`. Failing loudly is #170's own fallback ask, and it is strictly better than the previous silent success. If a consumer needs the incremental "boot the backend now, add the simulator later" flow, the route is devtrees-side filtering of the derived config (so unselected services are present but stopped, rather than absent) — a different design, deferred until someone needs it.

### Dead versus done

Reconciliation needs a definition of "dead" that does not mistake a finished one-shot for a crash. `Completed` with exit code 0 is a legitimately finished one-shot (a migration, a seed step) and is healthy. `Completed` with a non-zero exit or a signal exit — a killed process reports `-1` — is **dead**, as are `Failed` and `Error`. The #162 reproduction is exactly the `Completed`/`-1` case: `kill -9` produced `status: "Completed"`, which a check on status alone would have waved through. The JSON surface has the same hole: `health: "ready"` was reported for that dead process. The decision: devtrees reports health as not-ready whenever process-compose says the process is not running (`is_running: false`), in `ls`, `ls --json` and `up --json`, regardless of process-compose's stale `is_ready`. Health is never `ready` for a process that is not running (#174).

### Reconcile: restart dead services, never touch running shared ones

On a running worktree instance `up` **restarts dead selected isolated services**, then health-waits on them like a fresh start. If a restarted service does not become healthy within the wait window, `up` fails with `HEALTH_TIMEOUT` and leaves the instance running (ADR-0005); `SERVICE_START_FAILED` is only for the start request itself failing. These are this worktree's own processes, so restarting them touches nothing outside it.

**Dead selected shared services are restarted too** (#240), on the fresh and the running path alike. This section first said they were reported, not restarted: `up` failed with `SHARED_SERVICE_DEAD` and the remedy `devtrees down --shared && devtrees up`, because "a worktree-scoped command must not bounce a repo-wide process". That reasoning is about **bouncing a running** shared service, which would cut off the worktrees using it. A **dead** shared service has no users: every worktree that depends on it is already broken, and starting it again interferes with nobody. Refusing to do so left the only remedy, `down --shared`, which also stops every shared service that was still healthy under every other worktree — strictly more interference than the restart. One crashed shared database blocked every worktree on the machine until someone tore the shared instance down by hand (the motivating report). So the rule is now about the process's state, not its tier: **a running shared service is never stopped, restarted or reloaded by a worktree's `up`; a dead one is started again.** How:

- **Under the shared lifecycle lock, after the drift check.** The restart runs inside `ensureSharedStarted`, after the per-service drift check (ADR-0010). A restart runs the definition the shared instance holds, not this worktree's, so a selected service that drifted fails `SHARED_DRIFT` and **nothing** is restarted. A shared instance started by a devtrees that recorded no shared state (pre-#83) has no revision to check against, so its dead services are still reported (`SHARED_SERVICE_DEAD`, `reason: "unknown_revision"`).
- **Rows re-read under the lock, each dead service started once.** The decision is made from a `process list` read taken under the lock, so of two worktrees racing, the second reads the first's restart as running and starts nothing. The lock's wait budget became the worktree lifecycle lock's (~10s) so a concurrent `up` waits out a restart instead of failing `LOCK_CONTENTION`.
- **The same dead-versus-done rule** (`classifyService`): an exit-0 one-shot is done and never rerun, and a service process-compose is already `Restarting` is left to it. Only the selected shared services are considered (ADR-0010); one this `up` adds in the same call is started by the add's reload instead.
- **`process start` on the shared socket, in `depends_on` order**, before any add, so a service being added never waits on a dead dependency.
- **Health-waited like an isolated restart**, on the restarted services only, with `--wait-timeout` and the same stale-row rule (a restarted service's pre-restart dead row is ignored until it has been read alive or a dead row carries a new pid). The wait runs after the shared lock is released but before the worktree derives or spawns anything, so on the fresh path the worktree still starts only after its shared dependencies are back (ADR-0003).
- **Failures keep their own code where the remedy is the shared teardown.** A start process-compose refuses is `SHARED_SERVICE_DEAD` with `reason: "start_refused"` and process-compose's message (`details.start_failures`); `SERVICE_START_FAILED` was not reused because its remedy is the worktree `down` + `up`, the reason ADR-0005 gives for splitting codes by instance. A restarted service that dies again fails fast with `SHARED_SERVICE_DEAD`, `reason: "died_again"`. One that never becomes healthy is `HEALTH_TIMEOUT` with `details.instance: "shared"` and the `down --shared` remedy, the shared instance left running. A start process-compose answers with "already running" was someone else's and is not reported.
- **Reported**: the `up` envelope gains `shared_restarted[]`, the human summary a `restarted dead shared service(s): …` line, and `up --dry-run` previews the restarts as `would_restart_shared[]` (read-only; empty when the real `up` would fail `SHARED_DRIFT`).

`SHARED_SERVICE_DEAD` therefore remains only for what a restart cannot fix: a refused start, a restart that dies again, a shared service that dies during the cross-tier shared-health wait (`reason: "died_while_waiting"`, typically right after this `up` started it), and the stateless legacy instance.

## Supersedes #128

This ADR supersedes two parts of #128, the issue that introduced `namespace:` passthrough and `-n`:

- **"With no `-n`, all namespaces start (unchanged default)"** is replaced by opt-in namespaces: a bare `up` starts only `default`. The #128 default was chosen to leave existing configs unchanged, but it makes a namespace something you can only _subtract_, the opposite of what the motivating consumer (optional local backends) wants — a service declared as optional should not start unless asked for.
- **Its scope note** that changing the namespace set on a running instance is out of scope, and that "switching subsets is `down` then `up` with the new `-n`", is replaced by the explicit contract above: the unsupported case now fails with `NAMESPACE_NOT_RUNNING` instead of being undefined, and a bare `up` on a running instance has a defined target.

The rest of #128 stands: `namespace` is a process-compose-native key copied through the deriver (ADR-0002), the health wait's expected set is narrowed to the selected namespaces, and named ports are allocated and reserved regardless of which namespaces a given run starts.

## Considered Options

- **Keep "no `-n` means all namespaces"** (#128's default): rejected — it makes optional services impossible to declare. Any service in a named namespace starts on every bare `up` unless the caller remembers to subtract it.
- **Make `-n app` imply `default`**: rejected — it makes `-n` non-exact, so devtrees would no longer be forwarding what the user typed, and it leaves no way to run a named namespace without the default services. Exactness is also what lets the flag stay a verbatim passthrough.
- **Persist the booted namespace selection** (in the registry or a state file) and compare against it: rejected — it is a second source of truth that can disagree with what is actually running, and it would have to be written, migrated and cleaned up. Reading the selection back from the process-compose project is exact and stateless.
- **An "all namespaces" flag**: not added. Nothing needs it yet, and the spelling is cheap to choose once someone does.
- **Make `up` honest but not reconciling** (#162 ask 1: report and exit non-zero, never restart): rejected as the contract. It was the behaviour for shared services until #240. The restart is safe, and without it the only recovery for one dead process is an instance-wide `down` + `up` — in the reporter's stack that meant resetting a local database to bring back one Python process.
- **Restart dead shared services too**: first rejected — "a worktree-scoped command must not bounce a repo-wide process" — then adopted by #240, because that reason only covers a **running** shared service. A dead one has no users to cut off, and the alternative remedy (`down --shared`) bounces every healthy shared service as well.
- **Restart a dead shared service from outside the shared lock**, or without re-reading its state: rejected — two worktrees racing would both read it dead and both start it.
- **A `--no-restart` flag** to keep the old report-only behaviour: not added; nothing needs it yet.
- **Start the new namespace's services over the control socket** (#170 ask 1): not possible on v1.122.0, as above.
- **Support process-compose below v1.122.0**: rejected — the list form is what makes a service in two namespaces expressible, and the exclusion behaviour that makes bare-`up` target resolution exact was only verified from that version.

## Consequences

- **`up` can now fail on a running instance** where it used to print `is up.` and exit 0: for a dead shared service it cannot restart (since #240), for a restart process-compose refused (`SERVICE_START_FAILED`), for a restarted service that never became healthy (`HEALTH_TIMEOUT`, instance left running), and for an unbooted namespace. This is the intent, but a script that tolerated the old output will see new non-zero exits.
- **Existing configs change behaviour.** A stack whose services carry `namespace:` and which was started with a bare `up` used to start everything; it now starts only the services with no namespace, or fails with `NO_SERVICES_SELECTED` if there are none. The caller's fix is to name the namespaces with `-n`. This is accepted pre-stable (ADR-0005's walking-skeleton policy) and belongs in the release notes.
- **The booted selection is only knowable from a live instance.** Nothing records what a past run selected, so nothing survives `down`; the next fresh `up` starts from its own flags. That matches the instance lifecycle and is deliberate.
- **Dropped cross-namespace `depends_on` edges are another thing the derived config hides from `devtrees.yaml`.** Reporting them is part of the contract, not a nicety, for the reason ADR-0003 gives.
- **Four new error codes, additive under ADR-0005** (no `schema_version` bump): `NAMESPACE_NOT_RUNNING` (an `up -n` names a namespace the running instance did not boot; `details` carries the namespaces and the `down` + `up` remedy), `NO_SERVICES_SELECTED` (the selection resolves to zero services: a bare fresh `up`'s `default`, or an explicit `-n` naming only namespaces with no services), `SERVICE_START_FAILED` (the start command itself failed: process-compose refused or errored when `up` asked it to start or restart a selected service; `details` names the service), and `SHARED_SERVICE_DEAD` (a shared service is dead; `details` carries `{dead_services[], remedy}`, the remedy being `devtrees down --shared && devtrees up`; a code of its own because that remedy tears down a different instance, the reasoning ADR-0005 gives for `SHARED_START_FAILED` versus `WORKTREE_START_FAILED`). A service that starts but never becomes healthy, including one reconcile restarted, is the existing `HEALTH_TIMEOUT`, with the instance left running. Like `WORKTREE_START_FAILED`, they exist because agents branch on `error.code` and the distinction must not live in prose they would have to parse.
- **#240 changed what `SHARED_SERVICE_DEAD` means** without renaming it: it is now raised only for a dead shared service `up` could not repair, and `details` gained `reason` (`start_refused`, `died_again`, `died_while_waiting`, `unknown_revision`) and, for a refused start, `start_failures[]`. `HEALTH_TIMEOUT` gained `details.instance: "shared"` for a restarted shared service that never became healthy; the `up` envelope gained `shared_restarted[]` and `up_dry_run` gained `would_restart_shared[]`. All additive, no `schema_version` bump. A script that treated `SHARED_SERVICE_DEAD` as "run `down --shared`" still does the right thing; one that relied on `up` failing for any dead shared service now sees it succeed after the restart.
- **The health wait runs on a running instance too**, because success is defined as every selected service healthy on both paths. Per-service state in the `up` result on a running instance follows from that; it is not a separate output commitment.
